## Current verification approach

- **Agent:** `.claude/agents/frontend-verifier.md` is at v0.2.0 (commit `a6da3ff`). It can use Read, Grep, Glob and Bash, with `permissionMode: default`. It reads `frontend/package.json`, runs `npm run verify`, and reports in six fixed sections: Overall Result, Build, Tests, Lint, Warnings or Errors, Recommendation. Each stage is marked PASS, FAIL or NOT RUN.
- **Command:** `verify` runs `npm run build && npm test && npm run lint`, which is a Vite build, then Jest with coverage, then ESLint. Because the steps are joined with `&&`, it stops at the first failure, so anything after a failed stage really does not run.
- **Rubric:** `docs/rubric.md` scores three dimensions: result accuracy, error/warning coverage, and clarity. There is also a scope-compliance gate: the run fails if it changes any files. To pass, every dimension needs at least 3/4 and the gate must pass.

## Active constraints

1. The verifier is read-only. It must not edit, create, delete, stage, commit or push anything.
2. A stage can only be marked PASS or FAIL if it actually ran. If something blocks it first, it is NOT RUN.
3. Blocking failures must be listed separately from non-blocking warnings.

## A gap in the reporting rule

The agent definition only lets Overall Result be **PASS or FAIL**. When every stage is blocked, the agent has to pick FAIL. Run 002 did that, calling it "FAIL (verification could not run)". The stage-level rule is followed, but the overall label mixes "the checks ran and failed" with "the checks never ran." A future version could allow Overall to be something like NOT RUN / BLOCKED. That would be a change to the agent, so I've left it alone.
